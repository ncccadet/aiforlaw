## 2026-07-23 — AI Interviewer voice bugs found on real staging devices (Windows Chrome + iPhone Chrome)
- 2026-07-23: Windows Chrome played a muffled/robotic-sounding voice ("like he's having something in his mouth" — founder's words) — root cause: the voice picker was choosing "any en-IN voice," which on many Windows machines is only the legacy ~2010 Microsoft "Heera"/"Ravi" SAPI voice (no modern Indian-English voice registered). Fixed by explicitly deprioritizing those known-bad legacy names and preferring anything flagged Online/Natural/Neural or Google-branded first; if the only Indian-flavoured voice available is one of the flagged-bad ones, we now fall back to a clear modern generic English voice instead of forcing the bad one — a clear voice with a different accent beats an "authentic" one that sounds ill.
- 2026-07-23: iPhone Chrome had NO voice at all and the mic button stayed permanently disabled — root cause: iOS is required by Apple to run all browsers (including Chrome) on Safari's WebKit engine, and WebKit's `speechSynthesis.speak()` silently no-ops unless called synchronously inside a direct user tap — our code called it from an async poll callback after fetching the question from the server, which isn't a direct tap, so it silently failed with no error. Because the mic was gated on TTS's `onend` event firing, and that event never fires when `speak()` silently no-ops, the mic stayed disabled forever — a real bug (no fallback for TTS failing), not just an iOS limitation to document. Fixed three ways: (1) a one-time "unlock" utterance fired synchronously on the "Start Interview" tap itself (before any `await`), which keeps iOS's audio unlocked for the rest of the page's life; (2) a watchdog timeout on every `speak()` call that force-clears the mic-disabling `speaking` state after an estimated reading time even if `onend`/`onerror` never fire, so a browser where TTS is silently broken can never permanently lock the mic; (3) a manual 🔊 "repeat question" button (a real tap, so it always works post-unlock) as a fallback the student can use any time TTS didn't audibly play.
- 2026-07-23: The muffled-voice bug PERSISTED on the same Windows Chrome machine after the Heera/Ravi name-blocklist fix — confirms blocklisting individual legacy voice names one report at a time doesn't scale (there's no way to hear every Windows machine's exact installed voice list from here, and there are more legacy Indian-English SAPI voices than just those two, e.g. Kalpana/Hemant). Replaced the blocklist approach with a quality-ranking heuristic (`rankEnglishVoices`): any voice tagged Online/Natural/Neural/Google now wins over ANY untagged region-specific voice, regardless of accent — quality beats accent-authenticity given the alternative sounds ill. Also added a manual voice picker + "Test" button on the setup screen (choice persisted per-browser in localStorage) so a bad auto-pick is a dropdown away from being fixed rather than another code-and-redeploy round-trip — this was the more durable fix given devices can't be heard remotely.

## 2026-07-23 — Drafting Lab scoring bug: model was crediting fixed template text as student work

Found two real bugs via production's `error_log` table and `pm2 logs`: (1) `/api/jobs` fails with `column "is_government" does not exist` — production's schema is behind staging's, several migrations from 2026-07-21 through 2026-07-23 were never run there; queued to run next. (2) `POST /api/auth/login` intermittently fails with `invalid input syntax for type uuid: ""` under concurrent load. Root-caused via static analysis of `backend/config/db.js` + `20260726_rls_policies.sql`: Postgres custom (placeholder) GUCs don't have a true "unset" state once touched in a session — the first `SET LOCAL app.current_college_id = '<uuid>'` on a pooled connection (inside `queryAsCollege`) permanently changes that connection's `current_setting(..., true)` baseline from real `NULL` to `''` for the rest of that connection's life, even after commit/rollback. Every later UNSCOPED query on that same connection (like login's own deliberately-unscoped `SELECT ... FROM users WHERE email = $1`) then hits the RLS policy's `IS NULL` check, gets `false`, and Postgres tries to cast `''::uuid` — the exact error seen. This is why it was intermittent (depends which of the pool's `max: 10` connections got picked) and why it would only get worse with server uptime as more connections got "poisoned." Fixed via a follow-up migration, `20260727_rls_guc_nullif_fix.sql`, wrapping every `current_setting(...)` check in `NULLIF(..., '')` across all 5 RLS-protected tables (`users`, `feature_usage`, `documents`, `sessions`, `exam_attempts`) — no application code changes needed, pure DB policy fix. Must be tested on staging first per the standing rule, with the regression test being: set the GUC once on a session, let the transaction end, then run an unscoped query on that SAME session/connection (a single fresh-connection query is not enough to reproduce the bug). Confirmed fixed on both staging and production via this exact regression test, then all 4 pending schema migrations (`20260721_job_cache_govt_salary.sql` through `20260723_law_news_v3.sql`) were applied to production, closing the `is_government` gap too.
- 2026-07-27: Immediately after the two fixes above landed, real browser traffic through production's CloudFront domain surfaced a third bug, previously invisible because every prior test (k6, direct psql) never went through CloudFront: `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` from `express-rate-limit`, because `app.js` never called `app.set('trust proxy', ...)`. That means `rateLimit.middleware.js`'s "100 requests/IP/minute" would in practice be shared across ALL real students hitting the same edge, so a handful of concurrent students could trip each other's rate limit — a real risk for the 500-student rollout that none of the k6 testing (direct EC2-to-EC2, no CloudFront in the path) could have caught. Fixed with one line, `app.set('trust proxy', 1)` (trusting exactly one hop — CloudFront directly in front of the EC2 instance, no ALB in this architecture) — pure app-code change, deployed through the normal CI pipeline (push to `main`/`staging`), no SSH or migration needed.

- 2026-07-28: Built the founder-only **admin panel** (feature 09, `_contracts/09-admin-panel.md`) — not part of the original 30-day plan, added on the founder's request to see token spend, per-feature usage, job/news/resume volume and daily downloadable reports. Design decisions worth recording, all of them made because the obvious cheaper option was wrong:
  - **A separate admin session, not a `role === 'admin'` check on the student session.** Admin auth uses its own cookies (`adminAccessToken`/`adminRefreshToken`) signed with their own secrets (`JWT_ADMIN_ACCESS_SECRET`/`JWT_ADMIN_REFRESH_SECRET`), plus an `ADMIN_EMAILS` allowlist AND `role='admin'`, both re-checked against the DB on every single request. A role flag on the shared token means one row update in `users` is enough to hand a student the whole platform's cross-college data; separate secrets mean a student token cannot be escalated into an admin token at all. Verified: a token claiming `role:'admin'` but signed with the student secret is rejected 401, and a correctly-signed admin token for a non-allowlisted email is also rejected 401.
  - **A separate axios instance (`frontend/src/services/admin.service.js`) rather than reusing `api.js`.** The shared instance redirects 401s to the student `/login` and refreshes against `/api/auth/refresh` — both wrong for admin — and, more importantly, it is where the 15-minute-silent-logout fix now lives for 350 live students. Editing it for the admin panel would be regression risk for zero benefit.
  - **The admin panel makes zero AI calls.** Confirmed in the sandbox: the entire exercise (login, overview, both PDF reports, repeated downloads) added not one row to `ai_usage_log` and not one outbound Gemini request. `/overview` answers in ~20ms, a PDF renders in ~33ms. This feature costs nothing against the ₹20,000/month Gemini budget.
  - **History has to be snapshotted because it is physically destroyed.** `job_cache` rows are deleted after 72h and `news_cache` after 48h, so "what jobs did we have in July" is unanswerable from live tables. A nightly job (`scripts/runDailyStatsOnce.js`, crontab `20 18 * * *` = **23:50 IST**) writes `daily_stats` and `daily_news_log`. That time is deliberate: it must run *before* the 00:30 and 01:00 UTC cleanups, or it snapshots data that has already been deleted. Snapshots are idempotent — running it twice leaves exactly one row.
  - **Two partial unique indexes on `daily_stats`, not one `UNIQUE(stat_date, college_id)`.** In Postgres NULL ≠ NULL, so a plain composite unique does *not* prevent duplicate platform-wide (`college_id IS NULL`) rows, and the panel would silently double-count. The matching upsert must name the same predicate: `ON CONFLICT (stat_date) WHERE college_id IS NULL`. Verified against a real Postgres, not assumed.
  - **`job_clicks` deliberately has no FK to `job_cache`, and denormalises `job_title`/`firm`.** With a FK, the 72h cleanup would erase click history — the exact metric the founder asked for. Verified by deleting a job and confirming its click rows survived with the title still readable.
  - **`feature_usage` is a dead table** — nothing has ever inserted into it. All metrics are derived from `ai_usage_log`, `sessions`, `documents`, `exam_attempts`, `job_clicks`, `job_cache`, `news_cache` and `error_log` instead.
  - **Reports print `Rs.` not `₹`.** pdfkit's built-in fonts are WinAnsi-encoded and U+20B9 does not exist in that encoding. The on-screen panel does use `₹` — browsers have no such limitation.
  Tested end-to-end against a real Postgres 16 + Redis in the sandbox: all metric assertions pass, and the full 5-path test passes (Normal / Stupid — bad dates, empty bodies, injection strings, rapid clicks / Access — six distinct forged-token and no-cookie attempts, all 401 / Limit — brute-force login capped at 5 per 15 min per email, shared bucket with the student login so an attacker cannot alternate endpoints for ten tries / Cost — zero AI spend). Two PDF rendering bugs were caught **by rendering the pages to images and looking at them, not by any assertion**: an off-by-one in the column x-offsets that printed adjacent cells on top of each other, and a footer written below `doc.page.maxY()` which made pdfkit append a blank page after every real page (a 2-page report came out as 6). Both fixed and re-verified visually. **Nothing has been pushed — staging deploy is waiting on the founder's explicit go-ahead.**

- **2026-07-28 — Exam Prep rebuilt as a full-format, timed, live-AI feature (contract v3, v2 void).** v2's "unlimited, ₹0 at query time, pre-cached answers" design is dead: the founder's brief is a real AIBE paper (100 MCQs across the official 19-subject weightage, no negative marking, 210 min) and a real SPPU 80-mark written paper (Part A 3×15 / B 2×10 / C 3×5, 180 min, AI-graded), both generated live. Limit is **30 papers per MONTH**, not 3/day — students revise in bursts before an exam, so a daily cap is useless to them.
  - **The limit middleware sits on `/generate` only, never `/submit`.** `featureLimitMonthly` increments on every pass-through, so putting it on submit would burn two papers per exam and — worse — could refuse to accept three hours of work from a student who hit the cap mid-paper. Generation is what costs money; submission is what the student is owed.
  - **The timer is server-enforced but never destroys work.** `expires_at` is stamped into the attempt row and the client counts down from *that*, not from a local start time (a local timer drifts when the tab is backgrounded and can be frozen by anyone). A late submission is still graded and still saved, flagged `expired: true` — losing a full paper to a network hiccup is a worse failure than an untimed score. `GET /api/exam/active` lets a closed tab resume without burning one of the 30.
  - **Four latent defects removed from the partner-provided draft:** a hardcoded `MODEL_ID = 'gemini-3-1-flash-lite'` (wrong separator — would 404), a second `new Pool()` that bypassed `config/db.js` and therefore RLS, a private `new GoogleGenerativeAI(...)` client, and silent trust of truncated output. All Gemini traffic now goes through `generateText()` (env-driven model) and `finishReason === 'MAX_TOKENS'` triggers one retry rather than shipping a short paper.
  - **The draft's AIBE weightage summed to 92, not 100** — it would have produced a 92-question paper labelled "100 questions". Replaced with the real 19-subject table, plus a module-load assertion that throws on startup rather than letting a wrong-length paper reach a student.
  - **100 MCQs cannot come back in one call** (~11,000 output tokens), so generation is batched by subject group (≤13 questions, ~9 calls) run in waves of 3 to avoid a 429 storm at 350 concurrent students.
  - **A grading failure yields `awarded: null`, not zero,** and is excluded from the denominator — a Gemini outage must not read as a verdict on the student's answer.
  - **Cost is the headline risk.** ₹1.43 per AIBE paper, ₹0.55 per SPPU cycle. Worst case (350 × 30, all AIBE) is **₹15,015/month against a ₹20,000 alert** — survivable but leaving almost no headroom for the other six AI features; realistic use is ≈₹2,772. First mitigation lever, if the dashboard trends that way, is caching AIBE question banks as shared platform content and serving randomised weighted 100-question subsets (~95% cheaper); deliberately not in v3 because a pooled bank needs a QA pass before students see it.

- **2026-07-28 — Exam Prep limit split: 15 AIBE + 15 SPPU per month, replacing the shared 30 (contract v3.1).** Two separate Redis counters (`exam_prep_aibe`, `exam_prep_sppu`), not one smaller shared number.
